# Evidence-Bounded Interrupted-Operation Reconciliation

Task #11 is **partial**. `ReconciliationService` implements explicit, asynchronous recovery calls; `RecoveryEnvelope` records a strict observation recipe; `PaperRecoveryPort` supplies a one-attempt item observation/activation boundary. None is registered by the plugin entry point. There is no startup replay, recovery command, native repair permission, save scanner or new gameplay feature. The existing prototype still refuses mutations when its pending journal gate fails. No server data was inspected, changed, deployed or repaired by this implementation.

Tasks #9/#10 and G1 remain open. Service tests and API doubles do not accept native placement, independent world/player-save recovery or the already audited test environment. Preserve that environment and its scenario evidence; do not install this development candidate there to try to clear quarantine.

## Recipe is not observation or save proof

New item, fixture and structure producers now write a document-version-2 `ILR1` recovery envelope. Its bounded binary/base64 encoding holds action kind, immutable owner anchor, recipe profile, optional actor/slot/exact source bytes and the original version-1 caller evidence. The actor/slot is a transient operation source/destination reference, not permanent ownership or holder tracking. Original receipt evidence remains available so repeated normal service calls cannot acquire another physical-effect owner. Exact legacy terminal item receipts remain idempotent without becoming recovery authority.

The decoder rejects unknown document/wire versions, malformed fields, unsupported kinds, mismatched recipe/source profiles, invalid UTF-8 and trailing bytes. The service additionally checks the actual before/after forms, generation/revision progression, stable identity/HP/preferences/repair timer and location anchor. An envelope claiming an operation kind cannot change the journal's authoritative state. Bounds are the existing payload/component limits, not gameplay count limits. The Paper structure preparation checks the expanded evidence budget before spawning prospective stages.

Current `ItemLifecycle` drop/pickup captures the normal Paper actor/session/slot/source format; intentional loss records its named cause. `FixtureDelivery` captures its exact unavailable inventory bytes and delivery operation. `PaperStructureEffects` supplies typed source metadata to `StructureLifecycle`, which retains the request fingerprint and original physical evidence. Custom/opaque structure preparations produce an ADMIN recipe unless they explicitly supply the supported typed preparation. External removal, fixture activation review and structure activation review stay administrative. Existing version-1 journals are not rewritten or retroactively promoted into proof.

**An envelope never establishes matched saves.** `WorldPort.inspect` must independently establish exact BEFORE or AFTER physical state and coverage/provenance. `MATCHED_COMPLETE` is an obligation of a trusted observation adapter, not a claim made true by setting an enum or passing an envelope. It requires an actually inspected matching save/observation set covering all relevant source, target, stage and original-component evidence; a database-only copy, clean stop, matching baseline or loaded target chunk alone is insufficient. Unknown locations, unavailable players/chunks, mixed snapshots and unverified provenance remain incomplete or unmatched. No permissive production coverage callback is supplied.

## Recovery decision and durable phase matrix

`reconcile(operationId, port)` returns a future with a bounded generic diagnostic. Repository reads/writes run asynchronously. All inspection, revalidation and publication callbacks run through `WorldScheduler`; no world thread joins a database future. Callers keep gameplay unavailable until journals **and** unresolved physical staging/marker evidence have been assessed. Resolving one operation or receiving a terminal receipt does not grant global readiness.

| Journal/observation | Decision | Effects and durability boundary |
| :--- | :--- | :--- |
| COMPLETE or ROLLED_BACK receipt | TERMINAL, read-only | No world inspection/publication, activation, refund or replay. This is a receipt classification, not proof the current saves are consistent. |
| Unknown/legacy recipe, external removal, administrative review or unsupported state shape | ADMIN_REQUIRED | Preserve the operation and representation; do not infer a loss, adopt an archive or rewrite evidence. |
| World/chunk/player unavailable, incomplete coverage or UNKNOWN observation | WAIT | No force loading, source mutation or LOST transition. Retry requires a new observation, not replay of effects. |
| Unmatched save set, MIXED/ABSENT/unsupported physical evidence | ADMIN_REQUIRED | Absence alone is never proof of destruction. Keep journal and reservations inactive. |
| Exact BEFORE, independently matched complete scope, same owner evidence revalidated | ROLLED_BACK | Transition to RECONCILING if needed, then fresh-only guarded database rollback. Physical source must already be restored/proved; this service does not manufacture a refund or redo compensation. |
| Exact AFTER, independently matched complete scope, same owner evidence revalidated | COMPLETED | Advance INTENT/RECONCILING to EFFECTS_APPLIED if needed, then fresh-only guarded completion. Never replay the original apply callback. |
| Another journal/version/row wins | STALE | No publication or overwrite of the newer representation. Re-observe only through a new explicit call. |
| Database failure or unknown I/O outcome | UNAVAILABLE | Preserve evidence; do not retry effects or publish from an uncertain commit result. |
| Winning commit followed by failed owner publication | ADMIN_REQUIRED or STALE | Create an exact-row `reconciliation-review` intent only if that row is still current. Preserve its originating operation reference and existing stage; never overwrite a newer state. |

Every decision checks the exact operation snapshot, active-operation ownership, tower row version, generation, deployment revision and before state. A separate owner callback revalidates the physical observation and provenance before database finalization. Fresh-only `finalizeReconciliation` preserves the repository's existing completion/rollback guards but rejects terminal receipts; two coordinators cannot both interpret an old idempotent receipt as permission to publish. Existing low-level idempotent receipt methods remain available to their original callers.

The typed timed-exit recipe durably records the admitted cooldown duration. An AFTER observer proves the world effects and matching saves, and the fresh finalizer stamps the full duration from the recovery commit. A pending recipe with absent or opaque timing data remains administrative. BEFORE retains the original deadline, and terminal receipts retain their stamped deadline without replay.

Pending structure reservations retain the full before/after union through WAIT, ADMIN and failure. Verified finalization replaces it with the committed or rolled-back footprint in the same SQLite transaction. Successful database finalization is followed by an exact resolved-row read and owner publication check. Publication may only activate an already found exact stage; a failure freezes a new review without reissuing it. Compensation, completion and publication still do not form a shared transaction with independent Minecraft saves.

## Current producer and Paper support matrix

The built-in Paper port is one-shot per attempt, owner-thread-only and requires explicit coverage/provenance, authorization, effective ground-policy and existing-item admission callbacks. It reads only referenced loaded worlds/chunks, an online referenced player slot and exact ground entity identity. It never enumerates all saves, forces a chunk load, spawns an item, removes an entity, restores blocks or runs a generic old apply callback. Its bounded captured snapshot includes source bytes and current entity identity, item bytes, operation marker, position, staging/protection flags and nondecreasing ticks-lived. Provenance is rechecked with the physical snapshot and retained in the final operation evidence.

| Newly emitted recipe | Paper BEFORE evidence | Paper AFTER evidence | Remaining boundary |
| :--- | :--- | :--- | :--- |
| `item-drop` | Exact current source token/bytes in referenced slot and no target entity | Source slot empty, exact next-generation ground UUID/token/delivery operation, valid existing unavailable stage or already active representation | Source plus staged target is mixed; no automatic stage pruning. Moved/unloaded/uninspected source/target scope cannot become complete coverage by assertion. |
| `item-pickup` | Exact current ground UUID/token and empty destination slot | Ground source absent and exact resulting portable token in the referenced slot | No item is inserted or source removed by recovery. Unknown/mixed destinations require review. |
| Intentional `item-loss` | Exact original ground entity/token still present | Source absent only from an already EFFECTS_APPLIED intentional-loss operation with independently complete matched coverage | INTENT/RECONCILING absence alone remains administrative; external-removal evidence is ADMIN regardless of observed absence. |
| `fixture-item-delivery` | Proved pre-delivery empty slot | Existing exact delivery-marked bytes, or exact activated counterpart, in the referenced slot | Rollback retains the allocated generation-0 bootstrap row; no new item/identity is issued. Delivery marker is removed only from that existing item after winning completion. |
| Typed `structure-place/expand/compact/break/admin_recover` | A future full structure observation port must prove the actual original representation | A future full structure observation port must prove all named after effects | The built-in item port reports unsupported. Manifests alone do not prove old visual properties, sources, service shutdown or matched saves. Service tests use an explicit synthetic full observation. |
| Typed timed deployed exits in [Tower Health](TOWER_HEALTH.md) | A trusted full structure port proves the exact original representation and matched saves | A trusted full structure port proves the named after-effects and matched saves | BEFORE restores the original row. AFTER stamps the original admitted duration from the recovery commit and publishes once from the resulting receipt. The built-in Paper item port reports unsupported. |
| Legacy `item-place`, opaque source recipes, activation/reconciliation reviews | Not automatically supported | Not automatically supported | ADMIN; no metadata-based adoption or inferred replay permission. |

The authorization callback must compose current configuration/retirement/access/protection and recovery scope. It may not perform database I/O on the owner thread or bypass gameplay policy. A new coverage provenance value or changed physical evidence invalidates revalidation. Item lifetimes are not restarted: no `setTicksLived`, zero-age setter or replacement spawn is used. For an exact existing stage, normal lifetime/pickup policy is restored and the existing `PaperGroundItems` adapter is asked to validate/track that same entity. Native lifetime behavior across unload and independent saves remains a live gate. See [Paper's item implementation](https://github.com/PaperMC/Paper/blob/main/paper-server/src/main/java/org/bukkit/craftbukkit/entity/CraftItem.java); that online source rolls, while compilation uses this repository's pinned API.

## Completed-but-unactivated and audited cases

A crash after database completion but before activation can leave an unavailable stage with a terminal receipt. Repeating `reconcile` on that receipt intentionally does nothing. The existing loaded-item guard keeps such stages unavailable. A separately reviewed coordinator must preserve the stage and establish a new explicit review/disposition; it must not clear markers or repeatedly grant activation from the old receipt. If this service itself detects failed publication, its new review intent freezes the exact current row. Unknown or newer rows are never pulled back into the old operation.

The previously audited shared-world/database-swap evidence cannot satisfy this service's matched-save obligation. The active missing-entity loss quarantines remain administrative. Ground items belonging to archived scenario stores cannot be adopted into the active store or automatically pruned. The archived PORTABLE row whose item was cleared is not a journaled loss or proof of cleanup. The archived effect-denial pending pickup is a separate history and must not be merged with active loss operations. Four terminal LOST rows remain lifecycle history, not pending quarantine. Uninspected containers/dimensions remain UNKNOWN. A new snapshot can preserve the present inconsistency but cannot reconstruct an uncaptured consistent past. No live administrative recovery plan is approved or executed here.
